Overview

Watch the 79-second overview.

A short produced tour of what Strix does: the targets it scans, the agent team, validated findings and the viewer.

What you get

A pentest team you run from the terminal.

Not a scanner that dumps a list of maybes. Strix proves what's real, keeps the work on your machine, and fits the way you already ship.

Every finding is proven

Agents don't just flag a pattern. They build a working exploit and save the request and response, so you triage facts instead of guesses.

Runs in a local sandbox

The agents attack from a Docker container on your machine. No vendor cloud runs the scan. A local folder is mounted writable, so commit or stash first.

A viewer that explains itself

Run strix view for an overview, validated vulnerabilities, a live agent graph, run history and reports.

Drops into your pipeline

The -n flag runs headless and exits non-zero on findings, so a scan can gate a merge like any other check.

Reports you can hand off

Each run writes Markdown, HTML, per-finding notes and findings.sarif (SARIF 2.1.0) into strix_runs/.

Named specialist agents, working the target in parallel

A root agent maps the attack surface and spins up focused sub-agents: a recon pass, a CVE hunter, an injection prober. Each has its own transcript you can open and read.

How a scan runs

Three steps, start to report.

You point Strix at something you own. It does the attacking. You review what it proved.

1

Point it at a target

A local folder, a Git repository or a running web app. Add an instruction if you want it to focus on something specific, like one endpoint or an authenticated flow.

2

Agents work in a sandbox

The agents run inside a Docker container on your machine, mapping the attack surface, trying exploits, and validating what actually works.

3

Review in the local viewer

Run strix view for a dashboard with validated vulnerabilities, a live agent graph, run history and reports.

What you can scan

Code on disk, a repo, or a live app.

Same command shape, different target. Add --target-list to queue several at once.

A local folder

Point at source already on disk.

strix --target ./app-directory

A Git repository

Clone and scan straight from a URL.

strix --target https://github.com/org/repo

A running web app

Attack a staging URL end to end.

strix --target https://your-app.com

An authenticated flow

Hand it credentials for a test account.

strix --target https://your-app.com --instruction "test as user:pass"
Quick start

From zero to a first scan.

The first run pulls the sandbox image, so allow a few minutes. Your model settings are saved to ~/.strix/cli-config.json, so you only set them once.

Before you scan

  • Docker installed and running
  • Python 3.12+ and uv
  • An LLM API keyfrom a provider your team has approved
  • Permission to testwhatever you point it at

1 · Run a quick scan on the current directory

uv run strix -n --target ./ --scan-mode quick

2 · Scan only what changed against main

strix -n --target ./ --scan-mode quick --scope-mode diff --diff-base origin/main

3 · Open the results

strix view

Control cost and resumption with --max-budget-usd and --resume. The -n flag skips the interactive screen and exits non-zero on findings.

Data and privacy

You already know where your data goes.

Strix runs on your machine, but it isn’t air-gapped. Here is what stays, what leaves, and what the agent can touch.

stays local On your machine

  • The sandbox, where the agents run and attack.
  • Every finding, log and report in strix_runs/.
  • The viewer, which listens on 127.0.0.1 by default.

leaves Goes to your model provider

  • Agent prompts, which include the code and responses they are analysing, go to your model provider.
  • Anonymous usage counts go to PostHog and Scarf by default: versions, model name, scan mode, finding counts, token and cost totals. Set STRIX_TELEMETRY=0 to turn it off.
  • Point LLM_API_BASE at an approved internal endpoint or a local model such as Ollama or LM Studio if the code is sensitive.

Only test apps you own or have written permission to test. Strix runs real exploits against its target, and a local folder is mounted writable, so commit or stash first. Prefer staging and a dedicated test account over production data and real credentials.
